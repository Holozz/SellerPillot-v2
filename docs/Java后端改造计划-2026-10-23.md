## 2. 产品范围：保留业务，集中建设三条主线

服务对象仍为小型卖家的运营人员。需求属于个人项目设定，负载与故障由模拟实验构造，尚无真实生产流量证据。

本轮完整业务流程：登录 → 选择有权限的店铺 → 维护商品 → 导入订单和明细 → 查看经营统计 → 创建标题变更草稿 → 人工确认 → 查询回执与审计。

| 优先级 | 业务问题 | 方法与技术 | 预期效果及验证 |
| --- | --- | --- | --- |
| 必做 A：查询性能 | 数据增长后，多人反复查经营统计，重复关联聚合占用数据库资源 | MyBatis 明确 SQL、MySQL 执行计划、索引/查询对照、Redis 版本缓存、重建合并、回源并发限制 | 数字正确；分别测冷查询与热查询；给出吞吐、p95、错误率和 DB 负载，详见第 5 节 |
| 必做 B：业务一致性 | 多人确认同一建议、商品已变化、响应丢失后重试，可能造成错误修改或重复执行 | Spring 事务、固定锁顺序、商品版本、数据库唯一约束、幂等回执 | 重复确认只产生一次有效修改；旧版本冲突；提交成功后重试取得原回执，详见第 6 节 |
| 必做基础：导入与隔离 | 重复文件、同订单不同文件、错误明细、跨店铺参数篡改 | Spring Security 身份、服务层权限、业务键约束、解析与事务分离、单文件全有或全无 | 错误可定位；重复不重复统计；不跨店铺读写；导入和版本更新原子提交，详见第 7 节 |
| 扩展 C：异步报表 | 如果实测表明长区间导出阻塞普通查询，则后台生成报告 | MySQL job 状态、有限线程池、租约与条件发布；简单轮询不足时再引入 Outbox + Redis Streams | API 快速受理；进程中断后任务可恢复；旧执行者不能发布结果，详见第 8 节 |

**本轮重点完成“高性能经营查询”这一种场景，并用并发正确性和故障保护加强它。**50/100 个并发确认属于竞争条件实验，不等于证明高并发吞吐；缓存故障降级、worker 接管属于可靠性，不等于实现完整高可用集群。

本轮不新增支付、秒杀、抢券、外部电商写回、微服务拆分、注册中心、分库分表。保留 Python v2 知识/Agent 代码作为独立演示和参考；Java 主项目的投递门禁不依赖完成知识中心迁移或真实模型调用。

## 3. 技术栈及需要掌握的深度

| 层次 | 决定 | 选择原因、代价与需要解释的内容 |
| --- | --- | --- |
| 语言与 Web | Java 21、Spring Boot 4.x 稳定版、Spring MVC | 与当前 Java 技能和业务开发目标对齐；本机已有 JDK。先采用普通同步请求，掌握参数绑定、异常映射和生命周期，不因线程数量大就改用响应式或虚拟线程 |

## 4. 迁移边界与代码组织

### 4.1 运行形态及唯一写入权威

第一版为一个 Java 模块化单体：用户/店铺、商品、订单导入、经营查询、操作审批。高性能实验时启动两个相同 Java API 实例，共享 MySQL 和 Redis，用来检验缓存协调；它们不是两个领域微服务。

```text
React → Java API A / Java API B → MySQL（业务与权限事实）
                             → Redis（统计结果与重建协调）

Python v2 / 独立 Research Agent：保留独立演示，不直接修改 Java 业务库
```

Java 使用独立库 `sellerpilot_java`、测试库 `sellerpilot_java_test`、独立卷和 Compose 项目名 `sellerpilot-java`。建议新 API 用 8081，MySQL 用 3310，Redis 用 6383；实施前检查端口是否空闲，不覆盖当前 v2 的 8002/3309/6381/6382 或相邻 v1 的服务。

当前 Python v2 及其数据原样保留，迁移以导出的示例 CSV/脱敏夹具导入新库。Java 验收通过后明确切换前端代理目标并重新登录，避免两套业务后端同时写同一份业务表。

若以后需要 AI 接入，Python 仅返回分析/草稿内容，经 Java 接口授权、校验、落库并由用户确认。不要先让 Python 直写业务库，再宣称 Java 拥有统一事务边界。

### 4.3 接口兼容必须核对的内容

保留可复用的 `/api/auth/*`、店铺业务和 `/api/v2/stores/{sid}/metrics/query`、proposals 等已使用路径与字段；不是一开始迁移全部 v2 路由。形成明确路由清单，未迁移页面标记暂不支持，不让它们误连 Python 写接口。

- Java 支持当前登录 JSON 合同；现有密码为 Argon2、JWT 为 HS256 且包含字符串 sub 和 exp。新演示账号独立创建；若要迁移旧密码或 token，必须另做兼容测试，不把哈希算法名称相同当成自动兼容。
- 保持 FactCard 金额字段、UTC 时间和 `[start,end)` 口径；Java 用 BigDecimal 计算金额，避免前端数值精度变化。
- 兼容 FastAPI 现有 `detail` 字符串/CSV 行级错误结构，或同步修改前端解析；不要让业务错误退化成无法展示的默认 Spring 错误页。
- 手工草稿入口始终可用；Java 核心验收无需调用模型。

### 4.4 现有实现复核与 Java 版处理决定

2026-10-25 对 [Python v2](../backend) 做静态复核。下表包含已确认的实现差异、需要实验验证的条件性风险及可选改进；静态风险不等于故障已复现。优先处理与查询、审批、导入主线直接相关的事项，任务派发与预算优化跟随第 8 节扩展，不扩大本轮必做范围。

| 编号 | 现状、证据与结论边界 | Java 版决定 |
| --- | --- | --- |
| D1 | 同一业务动作两个写入口：[title_drafts.py](../backend/title_drafts.py)、[routers/titles.py](../backend/routers/titles.py) 与 [v2/actions.py](../backend/v2/actions.py) 都能改标题；v1 草稿只有 `pending/applied`，无幂等键、无执行回执表、无审计 | **P0**：只保留一个写入服务，旧入口下线并显式返回 410；路由清单里写明 |
| D2 | 统计合同分散：[analytics.py](../backend/analytics.py) 输出 gross/refund/net，[v2/metrics.py](../backend/v2/metrics.py) 的 sales 表示扣退款后的金额，Agent 工具仍走 legacy；字段不同不直接证明数值错误，但存在调用方理解不一致及维护分叉风险 | **P0**：明确字段语义，共用统计计算，核对相同样本和调用入口；旧入口在兼容切换后退役，不仅凭返回字段数量判定口径错误 |
| D3 | 缓存键未真正规范化：`sort_keys=True` 只排序 dict，`statuses` 是 list，`['paid','shipped']` 与 `['shipped','paid']`、`+08:00` 与 `UTC` 都生成不同键 | **P0**：键由显式规范函数生成（集合排序、时区归一、口径版本、limit），并加"等价请求同键"用例 |
| D4 | [v2/metrics.py](../backend/v2/metrics.py) 先读版本后查询数据，但这个顺序本身不能证明错配：同一只读 RR 事务的普通一致性读共享快照；RC 或跨事务读取才存在不同快照风险。当前未实测实际隔离级别及交错行为 | **P0 设计约束**：显式固定同一只读 RR 快照读取版本与数据，只回填该版本键；记录实际隔离级别和事务边界，分别验证 RR、RC/跨事务及旧查询晚回填。[MySQL 一致性读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html) |
| D5 | 缓存异常静默 `except Exception: pass`，无日志无指标，缓存故障不可见 | **P1**：降级必须记录 `cache_degraded` 与耗时；压测报告须注明命中与降级次数 |
| D6 | 草稿过期由 expires_at 检查并返回 409，未持久化 expired 状态；这不等于无法查询过期记录，主要问题是展示、统计与清理语义需要统一 | **P1**：读接口可按状态和 expires_at 派生过期状态，确认事务必须再次检查；确需持久化状态时由显式维护流程更新，不为查询强制引入写事务 |
| D7 | [jobs.py](../backend/v2/jobs.py) 的 dispatch_once 每次领取一条，但 [worker.py](../backend/v2/worker.py) 的 control 每轮最多调用 100 次；不能认定吞吐上限等于轮询频率，真实成本包含 DB/Redis 往返与每轮休眠 | **P2／扩展 C**：先测派发延迟、积压和资源；确有瓶颈再比较批量领取与 pipeline，并验证重投和恢复语义，不强制迁移任务基础设施 |
| D8 | enqueue 先锁 Store 行，再锁定读取 pending 并创建任务；所有创建入口遵循同一事务协议时，同店铺检查与创建被串行化，不能直接断言并发超 20。已知代价是锁粒度粗及扫描成本 | **P2／扩展 C**：先验证创建入口、事务范围与预算边界，测锁等待；只有测出瓶颈后才比较计数/条件更新，并检查失败回滚与计数漂移，不先替换正确性协议 |
| D9 | [v2/actions.py](../backend/v2/actions.py) 成功修改有审计，冲突、拒绝、过期缺少统一的结果追踪 | **P1**：成功审计与修改同事务；失败/拒绝通过结构化安全日志或独立短事务记录状态与原因，不能把失败审计放进注定回滚的业务事务后声称已保留 |
| D10 | `products.store_id` 可空：允许孤儿商品，`UNIQUE(store_id, sku)` 对 NULL 不去重 | **P0**：NOT NULL，迁移前清理孤儿行，复合外键全部保留 |
| D11 | 查询使用明确的 UTC 起止时间，未由 Store.timezone 推导店铺自然日；绝对区间查询不因此算错，但不能宣称已支持店铺本地自然日统计 | **P1 合同**：首版明确 UTC 绝对区间；若提供店铺自然日筛选，先转换 UTC 边界并测试夏令时和跨日，不因保留时区字段就宣称能力已完成 |
| D12 | 表名单复数混用（`store` vs `products/orders`） | **P2**：Java schema 统一命名，Flyway 一次建好 |
| D13 | 导入解析在事务内（[imports.py:98-99](../backend/imports.py)）：连接被占用解析上万行；错误列表无上限 | **P1**：解析与校验在事务外，错误超过 N 条后截断并汇总 |

## 5. 主场景：重复经营查询的高性能服务

### 5.1 业务及数据合同

场景为运营人员反复查看同一店铺近 7/30/90 天销售额、销量及商品排行。固定窗口容易重复；自定义窗口会产生不同查询键，需要单独测量命中率。它是待验证的使用假设，不是既有客户流量。

以固定随机种子生成总计 10 万、100 万条订单及关联明细，保留多个店铺、一个热点店铺、多明细订单、退款、取消订单、多个币种、倾斜商品分布。报告实际热点店铺行数，不能用全库百万条替代被查询的数据规模。已有 SQLite 造数记录不得充当本实验结果。

销售额按明细 `quantity × unit_price − refund_amount` 聚合；订单数避免 JOIN 多明细导致重复计数；不同币种分开；区间端点统一；确定排行并列时的稳定排序。优化前后必须返回相同结果。

### 5.2 分阶段对照，避免把缓存收益算成 SQL 优化

| 阶段 | 变化 | 必须保存的证据 |
| --- | --- | --- |
| B0 当前 Python 参考 | 只在依赖就绪时运行现有查询，记录已有索引 | 当前行为和查询结果；用于兼容参考，语言、连接池不同，不能单凭跨语言耗时归因 |
| J0 Java 正确基线 | 无应用缓存，保留合理的现有索引 | 与小样本手算/固定夹具相符；真实 SQL、索引及执行计划 |
| J1 SQL 与索引 | 每次只改变一个主要因素 | `EXPLAIN ANALYZE`、扫描/返回行、排序和临时表、写入代价及相同负载原始输出 |
| J2 版本缓存 | 只对确定的热点 QuerySpec 缓存 | 命中率、Redis 时延、聚合 SQL 次数、MySQL 轻查询开销 |
| J3 重建与保护 | 同 key 合并、回源预算、依赖超时和恢复 | 双实例热点过期、不同 key 冷启动、Redis 故障、队列/连接池指标 |

候选索引沿 `store_id`、状态、时间范围及关联键设计；根据选择性比较现有 `(store_id, ordered_at)`、v2 已有的状态/时间索引及必要的明细索引。不得删除合理索引制造虚假慢基线，也不保证加一个联合索引必然提升。

`query-plan.py` 现在测按币种聚合，`query-load.js` 请求按商品排行；Java 实验必须选择同一 QuerySpec，保存接口实际生成的 SQL，执行计划与负载结果逐一对应。[MySQL EXPLAIN 说明](https://dev.mysql.com/doc/refman/8.4/en/using-explain.html)

### 5.3 版本缓存的正确性合同

缓存键采用 `metrics:{store_id}:{data_version}:{schema_version}:{normalized_query_hash}`。规范化包含 UTC 起止时间、去重排序后的状态集合、指标、分组、limit 和可见范围；每个请求先查当前权限，缓存不能绕过授权。

所有会影响统计或返回字段的写入，在同一个 MySQL 事务中修改业务数据并递增 data_version。首版沿用一个店铺版本，接受标题变更也导致统计失效的额外开销；只有实测频繁失效后才拆 metrics_version。

一致性目标：写接口成功返回后才发起的新请求，读取主库取得最新已提交版本；与写入重叠的请求允许返回其读快照中的旧版本，并在 FactCard 中标明版本/时间。这里不是跨网络的绝对实时承诺。

缓存命中路径先在短 DB 读取中完成授权及版本获取，再查该版本的 Redis key。**命中仍然会访问 MySQL 权限/版本信息，不宣称缓存使 DB 请求归零。**

缓存未命中时，在独立、显式的只读 REPEATABLE READ 事务中读取版本和经营数据，使两者属于同一快照；事务结束后只写该快照版本的缓存键。如果重查得到版本变化，改查新键或按新版本重建，不用新版本键装旧数据。同事务里反复读取同一旧快照，不能当成“确认当前最新版本”。

旧键由 TTL 回收；不需要先删 Redis 再改 MySQL，也不依赖消息及时送达来保证新请求选择正确版本。缓存写入失败不回滚已提交的业务数据。

### 5.4 热点过期与 Redis 故障

- 先实现单实例同 key 结果共享；完成双实例实验前，明确它只能减少本进程的重复重建。
- 双实例使用每个统计 key 的 Redis `SET NX PX` 重建租约。取得租约后再查缓存；释放时原子校验持有者标识并删除，避免误删后续持有者的锁。
- 租约只减少重复工作，不承担当作数据库写锁的职责。租约过期时可能重复聚合，按版本键和快照合同保证结果正确，再以有限并发控制成本；不承诺任何故障下都只执行一次 SQL。
- 等待者只在请求预算内等待并重查；不能无限自旋、递归重试，或抢锁失败后全部直接查库。
- 每个实例为慢聚合设置独立许可，例如先试 1–2 个并发并由测量校准；Hikari、HTTP 工作线程及后台任务设置总预算，避免聚合等待占满全部数据库连接。
- Redis 超时后进入短暂退避的受控旁路，由本地重建合并和聚合许可保护 DB。超预算明确返回可识别的 429/503；恢复后重新填充缓存。依赖故障中的拒绝率必须公开。
- 本轮默认不跨版本返回旧统计。若改为逻辑过期/旧值降级，需要另写业务可接受的陈旧窗口、UI 标识和测试，不能悄悄改变一致性合同。

### 5.5 压测设计与预设门禁

测试环境冻结 CPU/内存限额、JDK、JVM、MySQL/Redis、连接池、数据清单、接口参数和代码版本；当前已有 Git，报告同时记录提交号及未提交差异。压测机与被测服务是否共用宿主机必须记录，不把同机结果外推到生产。

已有 constant-vus 脚本可作并发观察；新增 k6 arrival-rate 场景按 20/50/100/200 请求每秒阶梯测试，记录 dropped_iterations，避免系统变慢时发压速率也一起下降而掩盖饱和。[k6 到达率执行模型](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/arrival-rate-vu-allocation/)

| 实验 | 预设目标或判定方式（均未达到实测结论） |
| --- | --- |
| 结果正确 | 手算夹具、J0/J1/J2 查询结果完全一致，金额/币种/时间/多明细计数都通过 |
| 热点性能主门禁 | 在冻结环境、100 万总订单及明确热点分布、预热后，目标承受 200 请求/秒持续 5 分钟，业务 p95 ≤ 200 ms，非 200 或非法结果占比 < 0.1%，dropped_iterations 为 0；预热与正式区间分开 |
| 非缓存性能 | 单独测 J0/J1 的冷应用缓存查询，保留相同 SQL 结果、资源及 p95；目标降低已定位的主要瓶颈。基线已经足够快或优化无收益时照实保留，不编造提升比例 |
| 热点缓存失效 | 正常租约期内同 key 由一个重建者执行聚合；统计 SQL 计数验证。租约到期、慢查询和实例退出另测，公开重复与超时，不混入理想结果 |
| 冷键与混合流量 | 多个店铺/多个窗口低命中率；另加持续少量导入/更新，验证失效频率和池等待。不以纯热缓存成绩代表全部业务 |
| 写后可见 | 写入成功响应后发起新查询，返回新版本；构造“旧查询较慢、写入先提交、旧查询后回填”的竞争，确保旧结果不污染新版本键 |
| Redis 故障 | 固定相同请求负载下记录成功/拒绝/超时、聚合并发和 DB 连接使用；证明保护有效，不能隐藏 429/503 报告高吞吐 |

200 请求/秒与 200 ms 是本项目预设目标，不是已有能力或某公司统一门槛。M0/M1 基线后可依据硬件和业务调整目标，但必须在优化前记录理由；达不到时交付真实容量曲线和瓶颈，不事后降低指标冒充原目标已通过。

所有阶段至少报告成功业务吞吐、p50/p95/p99、失败与超时、命中率、聚合 SQL 次数、连接池 active/pending、DB CPU/锁等待、JVM CPU/堆/GC。大部分实现不必一次引入完整 Grafana 平台，先确保原始指标能采集并解释。

## 6. 第二主线：并发审批的正确性

业务场景：运营人员确认标题变更，页面重试或多标签页重复提交；其他人可能先改过同一商品。动作只作用于本地 MySQL，外部平台写回不在范围内。

迁移现有 `Proposal → Execution → Audit` 设计：草稿固定 product_version、载荷哈希、过期时间；执行表约束 proposal_id 唯一和 `(store_id, idempotency_key)` 唯一。

确认入口在一个短事务内：按固定顺序锁店铺 → 重新确认权限 → 锁草稿并核对确认载荷/幂等键 → 已执行则取原回执 → 检查草稿有效期 → 锁商品并检查版本 → 修改商品并递增商品/店铺版本 → 保存草稿状态、回执及审计 → 提交。等待模型、生成建议和网络重试放在事务外。

首版保留当前店铺锁策略，它同时简化权限撤销与写入的序列化；代价是同店铺不同商品也可能互相阻塞。必须测量锁等待，不把“有锁”写成高吞吐能力。只有需要提高写吞吐且测到该瓶颈时，另比较产品级条件更新和权限版本校验；不能直接删店铺锁破坏现有权限语义。

必要的 MySQL 实验：

1. 50、100 个并发确认同一草稿：仅一条有效修改、一条执行回执、一条对应审计；重试返回相同回执。
2. 幂等键关联不同载荷或不同草稿：返回冲突，不复用错误回执。
3. 同商品两个同版本草稿竞争：一个成功，另一个版本冲突；确认已成功草稿仍返回原回执。
4. 商品标题 A→B→A 后确认旧草稿：标题相同也因版本变化被拒绝。
5. 在写商品、保存回执或审计处注入异常：整个事务回滚；提交成功但响应丢失后，重试不再次修改。
6. 撤销成员权限与确认竞争：按锁定先后解释结果；撤销提交后新发起的确认不能成功。

保存每个请求状态、最终商品版本、执行/审计行数、锁等待和回执。不只断言 HTTP 200，也不使用 SQLite 的行为推断 InnoDB 行锁。[MySQL 锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

## 7. 必做基础：订单导入与权限合同

第一版保持现有业务语义：订单头和订单明细分两次导入，分别以单文件事务提交，**不宣称跨两个 HTTP 请求全有或全无**。明细不存在的订单不能凭空产生销量。

- 在数据库写事务外完成文件大小、行数、格式、时间、金额校验；沿用 5 MiB/10000 行上限作为起点，实测后再调整。
- 文件哈希唯一只识别“同文件重复”；业务唯一键 `(store_id, external_order_id)`、`(order_id, line_no)` 处理“不同文件同业务记录”。两种幂等必须分别验证。
- 延续当前订单状态/时间可以更新、既有订单币种不可改、既有明细行不可换商品的规则；保持按业务键更新，不把重复导入一律吞掉。
- 数据库内再核对店铺、订单、商品关系及权限；保留复合外键/唯一约束兜底。大小写、SKU 与时区规则与原系统一致或明确迁移差异。
- 有限批量 SQL 可以多次执行，但本轮单文件只有一次最终提交；批次中途提交会改变原子性，若未来大文件需要分批提交，另定义任务级成功/失败和读者可见规则。
- 导入记录、数据修改与 data_version 递增同事务；非法明细、重复请求、同业务键并发、数据库异常均检查最终数据和版本。

首版仍允许 owner 执行旧导入入口，其他角色权限按明确合同实现，不因从 owner-only 迁到 RBAC 意外扩大写入权限。跨店铺错误应避免泄露对方数据是否存在。

## 8. 扩展：长任务可靠性及可用性边界

只有必做 A/B 及基础链路验收后，才选一个异步报表任务进行 Java 深挖。其余 Python 文档/Agent 任务先保持原样。

先比较受限同步导出和 DB 任务表轮询：若后者已满足吞吐和调度延迟，采用 `FOR UPDATE SKIP LOCKED` 领取、短事务、有限执行线程、attempt/lease/token、退避重试和人工重试，不为简历强制引入新消息中间件。

如果轮询的扫描负载/任务延迟确实不足，再迁移已有 Outbox + Redis Streams 模式：同事务写 job/outbox，至少一次提示，DB 领取与对账，失效 token 拦截发布。Job/产物发布表由 Java 独占写入，不与旧 Python worker 混用相同任务。

报表文件先写 job_id/token 对应的独立临时产物；只有持有有效 token 的事务能发布最终指针，旧 worker 即使恢复也不能覆盖当前结果。外部文件与 MySQL 不属于同一事务，需要处理未发布临时产物清理。实验覆盖领取后退出、发布前退出、重复提示、过期旧 worker 和 DB 提交后的响应丢失。

可选启动两 API 实例，验证停止一个实例后剩余实例继续接受请求，报告在途失败和恢复时间；只能称为单实例故障实验。当前 MySQL、Redis、入口代理和宿主机仍是故障点，不宣称生产高可用、无损故障切换或全年可用性指标。

骨架阶段确认第 4.4 节的优先约束：单写入口、统计合同、缓存键规范化、快照内读取版本与数据、`store_id` 非空以及现有 Git 基线。表结构与接口合同先明确，审批和缓存的并发验证分别随 M2/M3 完成，不能把定义了字段或配置当成正确性已证明。

## 10. 验收证据与完成标准

每条主线留一份证据包：业务问题及来源 → 简单方案与不足 → 选择及代价 → 关键代码 → 复现步骤 → 原始结果 → 未覆盖边界。沿用[面试证据与实验规范](面试证据与实验规范.md)，本计划没有新增任何已测性能数字。

Java 主项目可进入简历前至少满足：

- 实际执行完整业务链，真实 MySQL 结果正确，核心跨店铺/角色权限通过。
- 导入的文件去重、业务键更新、回滚和版本更新有可复现结果。
- 并发审批的重复、冲突、ABA、异常回滚和响应丢失重试通过。
- J0/J1/J2/J3 保留可对照结果；性能主门禁未通过时明确写未通过，不称已实现预设容量。
- 热点失效、版本竞争、Redis 不可用有记录；依赖故障中的拒绝和超时公开。
- 提供固定依赖、独立 schema、演示数据、部署步骤和实际验证报告；任意脚本不能默认指向旧业务库。
- 能解释一个慢点或错误从何定位、为何选择方案、牺牲了什么；本地模拟流量/受控故障不写成真实线上业务。

扩展 C 或双实例故障实验只在完成后作为加分证据，不阻塞必做主线投递。Research Agent 的评测与故障证据单独维护，不与 SellerPilot 的性能指标混写。
