# SellerPilot 统一实施方案

更新日期：2026-11-02。

本文是项目唯一的更新方案与任务清单。当前进度以第 7 节概览为准；各阶段记录描述当时状态。勾选任务必须附带实现和验收证据，不能把设计写成已完成。现有代码的启动方式继续由根目录及前后端 README 维护。

## 1. 目标、业务流程与范围

面向同时经营多个平台、多个店铺的小型卖家，集中整理订单、退款和采购批次信息，以统一商品和人民币口径分析销售毛利，并通过 AI 解释有数据支持的经营变化。

完整演示流程：导入多店数据 → 确认商品映射与批次成本 → 生成销售毛利报表 → 查询与下钻 → 修正源数据并重算发布 → 对比差额 → AI 引用报表和明细解释变化。

三条交付主线：

1. **经营汇总与销售毛利分析**：平台文件适配、统一商品、人民币折算、采购批次成本、历史版本与差异追溯。
2. **报表高性能与必要保护**：预计算、原子发布、受限后台任务、查询资源保护、版本缓存、混合负载验证。
3. **AI 经营助手**：LangChain4j 接入模型，以受控工具完成查数、比较和下钻，答案绑定报表版本和证据。

本轮不接电商平台在线 API，不建设商城交易系统。第二条以高性能为主；不建设多实例任务抢占、租约续期、自动接管、断点续跑、复杂租户公平调度或数据库容灾。现有审批功能保留，但不扩展为本轮主线。暂不引入 Spring Batch、消息队列、分析数据库、向量数据库、复杂 RAG 或多 Agent。

## 2. 当前基线与技术选择

当前 Java 版本已有账号与店铺权限、统一 SKU、两套平台文件导入、不可变业务修订、跨店人民币销售毛利、汇率版本、固定汇率对比、成本重估、来源追溯及操作页面。旧单店统计、Redis 缓存和审批链路保留。销售及退货已支持按多个采购批次归属；新增报表已接入后台任务，混合负载验证和 Java Agent 尚未实现。旧接口性能结果不代表新报表性能。

现有边界：

- 订单和明细是两次独立导入，分别按文件事务提交；现有 upsert 会更新当前数据，不能直接当作历史事实存储。
- 写入先锁店铺，同店写操作串行；后台线程池不能消除该锁等待。
- 统计按单店查询；已有缓存版本、读权限校验和 RR 快照机制可以复用设计，但跨店报表不能简单拼接各店局部榜单。
- 已有缓存压测与并发实验仅证明旧查询链路，不能移用为新利润报表的性能结果。

| 层次 | 选择与职责 |
| --- | --- |
| 应用 | Java 21、Spring Boot 模块化单体；延续 Spring Security、MyBatis、Flyway |
| 数据 | MySQL 为事实和任务状态源；DECIMAL/BigDecimal 处理金额；不可变修订与报表结果保留历史 |
| 缓存 | Redis 缓存已发布报表；复用现有请求合并、重建互斥与有界回源 |
| 后台 | 单个后台执行实例、MySQL 任务表、有界队列、受限线程池；初期与 API 同进程，执行池独立 |
| AI | LangChain4j、一个支持工具调用的模型 API；先验证与当前 Java/Spring/Jackson 的兼容性再固定依赖版本 |
| 前端 | React/TypeScript；新增映射、成本、报表、任务与问答页面；任务进度用轮询 |
| 验证 | JUnit、真实隔离 MySQL/Redis、浏览器流程、k6、Micrometer；模型实测与 Mock 合同测试分开记录 |

## 3. 主线一：统一经营数据与销售毛利

### 3.1 导入、原始记录与权限

- 平台适配器将文件转换为统一的订单、商品明细、退款、退货、采购批次记录。保留原文件、文件哈希、适配器版本、行号和原始字段，计算明细可反查来源。
- 首版导入输入采用本方案定义的两套文件格式，平台差异通过列名和状态映射归一；本轮实现文件导入，不包含平台在线 API 同步。
- 文件级去重与业务级去重分开。业务键包含平台、店铺、实体类型和外部编号；明细使用来源提供的稳定子单或行标识，不能将重新排序后的物理行号当作稳定业务键。
- 订单、退款和采购批次更新形成不可变修订，保留来源更新时间、修订原因及操作者。有可靠来源版本时拒绝旧更新；没有时对冲突显式确认，不以“最后上传”默认为业务最新。
- 新导入先落暂存区，解析、校验和关联检查通过后发布批次。失败批次不参与新报表，不能因分批提交而暴露半文件。原始文件采用服务端生成路径和持久卷存储，数据库保存元数据与哈希。
- 第一版以现有店铺 owner 作为内部商品及成本配置的业务边界，同 owner 的多店可汇总；查看、任务提交、重试、报表和明细下载均校验全部目标店铺权限。跨 owner 组织协作另行设计。
- 创建/发布配置与导入默认由店铺所有者执行；已有只读成员仅能读取其全部有权访问的目标店铺报表。权限变化后重新校验，不能用旧任务、会话或缓存绕过撤权。


首版平台文件按以下两套输入格式映射到统一语义合同。每条源记录保留平台、店铺、来源文件哈希、来源行号和原始字段。

| 文件实体 | 必需业务字段 | 规则 |
| --- | --- | --- |
| 订单 | `external_order_id`、`ordered_at`、`paid_at`、`status`、`currency` | 业务键为平台＋店铺＋外部订单号；时间含时区；订单货币作为明细金额默认币种 |
| 商品明细 | `external_line_id`、`external_order_id`、平台商品/SKU、`quantity`、`unit_price`、`discount_amount`、`currency`、`source_batch_id` | 行 ID 在来源中稳定；采购批次 ID 必须能关联采购批次；同一行拆自多个批次时提供多条批次分配及数量 |
| 退款/退货 | `external_refund_id`、`external_line_id`、`confirmed_at`、`refund_amount`、`currency`、`returned_quantity`、`restocked` | 退款与退货分别记录；无退货的退款数量为零；退款业务键在来源范围内稳定 |
| 采购批次 | `source_batch_id`、平台/店铺、SKU、`received_at`、`quantity`、`unit_purchase_cost`、`currency` | 批次业务键为平台＋店铺＋来源批次号；原币金额与币种保留，报表按采购确认日汇率换算成人民币 |
| 汇率 | `base_currency`、`quote_currency`、`effective_date`、`rate`、`source` | 方向固定为 1 单位 base 等于 rate 单位 quote；同币种汇率为 1；保存发布日期和修订版本 |

平台状态、日期、折扣/退款含义由适配映射到统一定义；不明确时拒绝发布或标记待核对，不猜测。销售收入按付款日，退款按确认日；折扣只扣一次。批次分配数量必须等于明细销售数量且不能超过批次可用数量。跨币种计算统一以人民币为计算和展示币种，同时保存原币金额、实际采用的汇率日期与汇率版本；汇率缺失的记录不能进入“完整人民币销售毛利”合计。

### 3.2 统一商品与组合装

- 建立内部 SKU、规格和基础计量单位，维护 `(业务范围, 平台, 店铺, 外部SKU) → 内部SKU` 的版本化映射。
- 同名不自动合并；未映射记录进入人工确认列表，显示数量与金额。店铺总额仍包含其数据，但商品分析归入明确的“未映射”类别，避免静默漏计。
- 组合装保存组件与数量关系；销量按基础单位展开。商品利润归属另保存组合销售额分配权重，权重须守恒；不得把整套收入复制给每个组件。
- 更改映射生成新版本，旧报表继续使用旧映射。循环组合、单位不兼容、缺少分配依据必须明确拒绝或标为待处理。

### 3.3 币种、时间与两种口径

统一存储 UTC 时间，报表记录业务时区并用左闭右开区间。第一版销售确认以付款日为准，退款按退款确认日处理；缺少必要日期的源文件需补齐或列为不可计算，不静默使用导入时间或下单时间替代。

| 口径 | 规则及用途 |
| --- | --- |
| 交易日折算 | 销售收入与退款按各自确认日期取汇率；用于观察对应期间的经营结果 |
| 固定汇率对比 | 比较期间共用同一组固定汇率及版本；展示排除汇率折算变化后的差额，不宣称已经解释全部业务因果 |

汇率保存原币、目标币、方向、有效日期、来源、抓取时间和修订版本。先确定一种有稳定历史数据合同的来源，使用定时任务和 HTTP 客户端拉取；离线测试用固定夹具，手工导入须注明来源。非交易日只允许按规则采用最近已公布汇率并显示实际日期；其他缺失不得按 1 折算。

金额与汇率使用明确的 DECIMAL 精度，Java 使用 BigDecimal；保存原币金额及中间高精度值，报表折算为人民币并使用固定舍入规则。缺汇率时展示未折算金额与覆盖范围，不能把小计标成完整销售毛利。



### 3.4 销售毛利与完整度

```text
销售毛利 = 销售收入 − 折扣与退款 − 已售商品对应采购批次成本
```

本项目的利润范围仅为销售毛利。采购批次成本来自导入数据，并关联到对应销售明细；不在本轮计算采购附加杂项、平台佣金、支付费、履约物流或广告等其他成本，也不将结果称为完整经营利润或会计净利润。源销售金额是否已扣折扣、退款必须由导入合同明确，避免重复扣减。

- **批次成本**：销售明细按来源提供的批次信息关联采购批次；一笔销售可拆分消耗多个批次。保存批次、数量、单位采购成本及分配结果。来源未提供可用批次关联时标记待处理，不擅自推断实际批次。
- **历史快照**：销售明细引用销售时对应的批次成本修订。修改采购成本不覆盖旧报表；修正后创建新版本并可追溯差异。
- **退款与退货分开**：退款冲减销售收入；只有来源确认退货入库时才转回对应批次成本，并校验退货数量和金额边界。
- **人民币口径**：报表统一以人民币展示。原币销售金额按交易日汇率折算；固定汇率对比使用指定汇率版本。保存汇率来源、日期与版本，缺失时按原币列示并标注未折算，不能默认为 1。
- **完整度**：记录商品映射、批次成本及汇率的覆盖率，并同时给出数量和金额分母。存在待映射、缺成本或缺汇率时显式标识，不能把不完整小计展示为完整销售毛利。

### 3.5 历史可解释与可复算

报表任务固定 `input_manifest`：目标店铺有序集合、各店已发布源批次/修订边界、商品映射版本、采购批次成本版本、汇率集、计算规则版本、时间区间、时区、币种与分析口径。

先在同一个 RR 快照中取得权限和上述版本边界，再使用不可变记录计算；不在长计算、文件解析或模型调用期间持有数据库事务。仅保存一个 `data_version` 而不保留对应历史事实，不满足复算要求。

保存汇总、商品/店铺维度结果及必要的计算明细：原币金额、汇率、批次成本分配、源记录和舍入依据。修正生成新版本，原报表不覆盖；跨店先聚合完整候选再排序，不合并局部 Top N 冒充全局榜单。

对比报表要求店铺集合、期间定义、口径等可比；数值变化分解由确定性后端完成。收入、退款、批次采购成本与汇率影响分别展示；多因素同时变化时固定分解顺序并展示规则，使差额能够核对。

## 4. 主线二：高性能及最小必要保护

### 4.1 最终五项范围

| 必做项 | 实现程度 | 验收重点 |
| --- | --- | --- |
| 报表预计算与发布 | 独立版本结果及明细，全部成功后短事务更新发布指针；页面展示版本、源数据时间和完整度 | 查询无需重新计算全部利润；计算中/失败时旧版本仍完整可读 |
| 可重试的后台任务 | 单个后台执行实例；MySQL 保存状态、固定输入、规则版本与重试次数；同输入重复提交复用任务；重启后识别中断任务，用户整批重试 | 不重复发布，不因失败遗留半报表；无租约和自动接管 |
| 查询与重算资源保护 | 独立受限执行池、有界队列；限制后台并发与数据库连接占用，为前台保留预算 | 查询与导入/重算并存时延迟受控，后台也有进展 |
| 报表查询与热点保护 | 查询索引、分页、版本缓存、请求合并、持有者校验释放及有界回源；读取仍检查权限 | 集中访问不会重复触发昂贵计算或绕过权限 |
| 混合负载与失败验证 | 查询、导入、重算并行；检查重复提交、中断、重启后整批重试和发布完整性 | 同时记录查询质量与任务完成情况，不只测试热缓存 |

### 4.2 任务状态与发布边界

任务状态：`QUEUED → RUNNING → SUCCEEDED / FAILED`；进程重启发现遗留的 `RUNNING` 时标为 `INTERRUPTED`，由有权限用户重试为 `QUEUED`。正常排队任务可继续调度。部署保证只有一个启用后台执行的实例，更新时旧进程退出后才能启动新的后台执行者；不支持重叠部署后的自动接管。

- 任务唯一键由业务范围、类型、规范化参数、输入清单及规则版本构成，数据库唯一约束兜底。重复请求返回已有任务，已有失败任务返回状态及重试入口。
- 整批重试复用固定输入；选择最新数据需要创建新任务。每次尝试写入独立的未发布结果区域，失败遗留内容不会被查询接口读取。
- 发布事务同时检查任务仍处于预期状态、结果完整、当前权限以及期望发布基线，再更新发布指针和成功状态；结果唯一约束防止重复发布。
- 同一报表系列有多个输入版本时，旧任务晚完成不能覆盖更新的已发布版本；通过期望发布版本的条件更新判定，失败竞争的结果仍可作为历史结果查看。
- 提交成功但响应丢失时，重复请求或任务状态查询返回已完成结果；不再次计算或发布。
- 导入采用持久化暂存与批次发布，发布时短暂锁定店铺并递增源版本。不要将整段解析或计算置于现有店铺锁内。
- 队列上限同时约束数据库待执行任务数量，不能只限制内存队列却无限接收数据库任务。超出容量时返回明确的忙碌响应和重试提示。

### 4.3 查询保护与观测

后台初始并发为 1，基于实测再调整；采用独立、受限的后台连接池或等价的后台数据库连接准入机制，记录前后台连接预算。线程池独立不代表数据库资源已经隔离；CPU、I/O 与锁等待仍需实测。

已发布报表缓存键包含业务范围、报表版本和规范化查询条件。获取最新报表必须检查当前发布指针，历史报表明确展示数据截止时间；撤权后不能命中旧授权缓存。没有历史报表时显示未生成或计算中，不用其他报表冒充结果。

Redis 故障沿用现有有限等待与有界回源，不承诺全部请求成功；MySQL 不可用时不得绕过权限检查返回缓存。缓存租约用于减少重复读取，不作为报表发布正确性的保障。

观测至少包括：前台 p95/错误率/拒绝量、连接池等待、SQL 耗时、缓存命中与回源次数、任务排队/运行时长、队列长度、任务成功/失败/中断数、CPU/内存与数据库负载。

## 5. 主线三：AI 经营助手

### 5.1 功能流程与工具

以“销售额上涨但销售毛利下降，排除汇率影响后主要变化是什么，哪些商品的采购批次成本缺失”为代表任务：确认范围 → 检查完整度 → 比较报表 → 下钻主要差额 → 引用依据回答。

| 工具合同（拟定） | 作用 |
| --- | --- |
| `query_profit_report` | 查询指定版本、店铺集合、期间与口径的经营结果 |
| `get_cost_completeness` | 查询缺失、暂估及未映射项，返回分母与覆盖范围 |
| `compare_reports` | 确定性计算可比报表差额及固定汇率对比结果 |
| `drill_down_evidence` | 查询差额对应订单、成本、费用、汇率与来源行 |

模型负责理解问题、选择工具和解释；金额、排名、成本分配和差额分解由 Java 服务计算。资料不足时说明缺失，不能推断没有访问量/投放数据支持的经营因果。

### 5.2 工程边界

- Java 内接入 LangChain4j；先用一个模型完成工具调用、结构化输出、超时和 usage 探针，验证后固定依赖。参考 [旧版 Agent](https://github.com/Holozz/SellerPilot/blob/main/backend/agent.py) 的白名单和参数校验，不恢复旧 Python 业务服务。
- 身份来自服务端；每个工具校验目标店铺及报表权限，参数使用白名单与范围限制，不允许模型自由执行 SQL。
- 本轮分析固定报表版本；比较明确指定两个版本。历史对话只辅助理解，不能替代当前数据依据；用户要求最新数据时重新选择版本并说明变化。
- 日期、店铺或币种不明确时澄清；回复包含使用口径、报表 ID/版本、证据引用、数据完整度和未覆盖事项。
- 对话按用户和业务范围隔离；工具结果、商品标题及文件文本都是数据，不能改变系统规则。
- 工具调用数、模型轮数、总时长和输出长度均有上限；模型调用使用独立并发限制，不持有数据库连接等待模型响应。超时返回受控错误，普通报表不受影响。
- 首版只读工具，不让模型直接导入、改成本、发布或重算；用户可通过页面显式发起这些操作。
- 记录工具参数、报表版本、耗时、返回证据、模型与 Token 用量和失败类型；轨迹不记录密钥及无关敏感字段。

单 worker 串行执行，领取、读取输入和发布依次使用数据库连接，后台 worker 同时最多占共享 Hikari 池的 1 条连接，池上限 12。报表计算与 JSON 序列化在事务之外，快照读取事务超时 15 秒。当前输入上限为 20 店、366 天和 10000 条销售及退款事件。上限是输入保护，实际吞吐和延迟需以数据规模实验为准。独立发布指针和大规模混合负载尚待验收。

随后在同一集成用例中加上预热与纯查询对照。每组 4 个客户端各连续发送 20 次相同查询，混合组导入区间外的 500 条订单，重估另一店铺的一条明细。纯查询 51/80 次触发前台聚合限流，成功请求 p95 25 ms。混合组 55/80 次触发同一限流，成功请求 p95 28 ms，导入成功，重估提交至读取耗时 547 ms。纯查询已出现大量拒绝，单次小样本无法量化后台工作的边际影响。该实验采用闭环请求，Redis 关闭，报表规模仅一条销售明细。

16 项 MySQL 业务集成测试通过，前端构建及 2 项接口替身浏览器用例通过。

## 8. 验收标准与证据

### 8.1 正确性先于性能

| 方向 | 必须记录的结果 |
| --- | --- |
| 统计正确性 | 人工样本差额；重复导入/重试前后结果；订单与明细计数；批次成本分配及组合收入分配守恒 |
| 数据完整性 | 映射、成本、汇率覆盖率及明确分母；未知/零/暂估区分；未折算金额按原币展示 |
| 历史追溯 | 同版本复算一致；旧报表不变；修正能追到源记录与计算规则 |
| 权限与发布 | 全店权限检查；撤权后缓存/历史/Agent 不再可读；半结果不可见；旧任务不覆盖新版本 |
| 任务失败 | 重复提交、数据库提交后响应丢失、计算中断、重启识别及人工整批重试；只有一个有效发布结果 |
| AI | 固定题集的数值正确率、证据匹配、完整度提示、越权拒绝、时延、调用次数及 Token 成本 |

### 8.2 性能和混合负载

先记录机器、店铺数、各店数据分布、订单/明细/费用规模、查询跨度、后台任务输入及缓存状态。数据规模不等于请求速率，旧热点数据集不等于新利润查询的工作集。

四组实验：

1. 相同查询下分别测冷缓存、热缓存，记录 p95、错误、拒绝与回源；索引变更保留执行计划和对照。
2. 同样前台负载叠加订单导入、利润重算，记录查询退化、任务排队/完成时间、连接池等待和 CPU/数据库负载。
3. 并发提交相同任务、并发读取新发布报表，验证去重、单次有效发布和热点保护。
4. 中断单个后台执行进程，重启后整批重试；检查已发布旧报表不变、新结果完整且不重复发布。

初始待测目标：固定环境与代表性查询下，热缓存报表在 200 req/s、5 分钟的查询及混合负载实验中 p95 ≤ 200ms，业务失败率 < 0.1%，无丢弃迭代；后台任务必须完成并记录耗时。若基线不满足，保留失败并分析后明确调整目标，不能悄悄降低负载。冷查询单独报告，不套用热缓存门槛。

统计非 2xx、结果不一致、过载拒绝及超时，拒绝量单列但也计入业务失败；不只报告成功请求延迟。后台吞吐、排队时间与前台延迟同时报告。不预设真实用户节省时间，业务收益需真实对照实验才能填写。
