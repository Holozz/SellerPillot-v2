# SellerPilot 面试证据与实验规范

目标是解释一个真实需求与工程决策，并用可复现结果支撑；不以测试数量、覆盖率、容器数或合成订单量代替能力。

## 五个优先案例

| 案例 | 面试要回答的问题 | 基线与备选 | 实验与结果文件 |
| --- | --- | --- | --- |
| 经营查询 | 为什么慢？索引如何选？缓存是否掩盖低效 SQL？ | 原始 SQL、索引、查询重写、缓存分别测量 | seed manifest、EXPLAIN ANALYZE、k6 原始输出、冷暖缓存与错误率 |
| 任务恢复 | DB 与消息如何一致？重复投递与旧 Worker 如何处理？ | 同步处理、简单队列、outbox+租约的边界比较 | 故障点、job/token/outbox、尝试与最终产物数量 |
| 并发审批 | 版本与幂等分别解决什么？为什么标题相等仍可能过期？ | 原值比较、版本控制、短事务 | A→B→A、同商品两草稿、50并发确认、响应丢失重试与实际回执 |
| 知识检索 | 哪类问题适合哪种召回？融合与重排值得吗？ | 同题四策略、固定长度与条款分块 | 开发/保留集、原始排名、Recall@5、MRR、无答案与错误引用、延迟与成本 |
| Agent 定位 | 答错源于模型还是工具？如何限制权限、成本与循环？ | 固定流程、单 Agent、有限组合流程 | 任务成功、字段正确、证据支持、无效工具、预算、轨迹和真实模型用量 |

## 实验记录模板

1. 业务问题及来源：用户反馈、开发发现、负载实验或受控故障，准确标注。
2. 正确结果和可证伪的假设：先定义验收，再选择技术。
3. 环境：提交版本、CPU/内存、依赖、数据库参数、模型与 Prompt、数据与种子。
4. 基线与备选：为什么简单方案不足，复杂方案多付出什么代价。
5. 复现命令与原始证据：请求、事件、SQL计划、任务/产物记录、延迟分布和错误。
6. 变化：关键代码、修复提交、相同条件复测。失败或无提升也保留。
7. 结论与限制：只对测试范围下结论，不把本地合成数据写成真实生产规模。
8. 简历句子：问题→本人实现→实测或可演示的结果。

## 现阶段验证边界

tests_v2 默认使用独立临时 SQLite、内存 Qdrant 和显式 Mock 模型验证业务合同。它们能发现权限、统计、版本与状态机错误，不能证明 MySQL 行锁、多进程 Redis 恢复、真实语义检索或生产吞吐。

MySQL 并发实验、真实 Redis Streams 认领、S3 与远程 Qdrant、真实模型与人工标注题集必须另行运行，报告分开。CI 内有真实服务同样不代表本机已经运行过。

## 数据与性能

seed_v2.py 可以分批生成最多200万条订单及关联明细，固定随机种子并保存 as_of；数据分店铺和商品倾斜，一单多明细。造数成功只证明数据集可构造，不等于查询优化有效。

query-plan.py 在 MySQL 保存单次查询和计划，不将一次耗时冒充 p95。query-load.js 使用多个区间查询，测试5/10/20并发与不同缓存状态；相同环境比较各阶段，报告吞吐、错误与资源。百万订单与20个虚拟用户是规模和负载，不能写成百万用户或生产高并发。

## 检索与 Agent 题集

retrieval.py 读取人工复核 JSONL，字段为 id、question、relevant_chunk_ids、answerable、split。先发布资料，导出 chunk ID 后标注；未经检查的自动生成题不作为标准答案。开发集调参，保留集冻结后测量，反复调整需更换保留样本。

hash embedding 仅为离线词特征夹具，报告将 quality_claim_allowed 标为 false。重排服务未配置或失败时不宣称运行了重排；报告实际降级和应用数量。权限题单独测试泄漏，答案语义支持需人工评审，不能由合法引用 ID 推导。

## 简历与面试交付

每个案例至少有一份决策记录、一条复现命令和一份可核验结果。投递时挑3–4项与岗位相关的贡献；不强行把所有技术写入简历，不保留此前预填的性能数字。准备三分钟解释和关键代码入口，再接受从事务、锁、版本、统计粒度或失败路径的追问。
